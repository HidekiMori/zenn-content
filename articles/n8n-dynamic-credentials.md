共有する価値のあるワークフローを作り上げ、それは完璧に動作しているとします。——他の誰かがそれをインポートするまでは。

ボトルネックになるのは、常にAPIキーです。あなたのキーをそのまま使えば、すべてのユーザーの利用料があなたのアカウントに請求されてしまいます。かといってユーザー自身のキーを使わせようとすると、彼らはワークフローをインポートするたびに設定画面を開き、キーを貼り付け、ノードを再接続しなければなりません。どちらの方法も、スムーズな体験（摩擦のない利用）とは言えません。

よりスマートな選択肢は、ワークフローがフォーム上で直接キーを入力するように求め、そのキーを認証が必要なHTTPノードへと裏側で受け渡すことです。これは、一見難しそうに思えるかもしれませんが、実際には非常にシンプルです。

この記事では、実際に動作するクレデンシャルの設定パターン、ノードが1つだけの場合の代替案、落とし穴、そしてカスタムノードの作者にとってこれが何を意味するのかについてのメモを順を追って解説します。

> 以下のスクリーンショットは、n8nに組み込まれている「Bearer Auth」クレデンシャル、および `n8n-nodes-ldxhub` パッケージ固有のクレデンシャルスキーマのものです。手法自体は汎用的なものであり、ここで紹介する内容は、任意のHTTPノードを使用したワークフローや、式（Expression）モードに対応したカスタムノードであればどれでも機能します。

## フォームが問いかけ、クレデンシャルが聴き取る

最もシンプルなケースを考えてみましょう。Form TriggerがAPIキーを収集し、HTTPノードがそのキーを使って認証が必要なエンドポイントを呼び出すという構成です。2つのノードの間に1つの架け橋を架けることになりますが、この架け橋は直接的な「式（Expression）」で繋ぐのではなく、クレデンシャルを経由させます。

大まかな流れは以下の通りです：

1. Form Triggerで `api_key` を収集する（入力値を隠すために `Password` エレメントタイプを使用します）
2. Bearer Authクレデンシャルが、式を介してそのフォームの入力を参照する
3. HTTPノードがそのクレデンシャルを選択する

Form Triggerの設定は直感的です。フィールドを1つ追加します：

```
Form Trigger
  Form Fields:
    - Label: API Key
    - Element Type: Password
    - Custom Field Name: api_key
    - Required Field: yes
```

エレメントの種類（Element Type）が重要です。`Text` ではなく `Password` を使用することで、画面上に入力値がマスクされて表示されるようになり、ブラウザを覗き見されてもキーが露出するのを防ぐことができます。

ユーザーがワークフローのURLを開いたときに表示されるフォームは以下のようになります：

## クレデンシャルを「式（Expression）モード」に繋ぐ

現代のほとんどのAPIで採用されているBearerトークンの場合、**Bearer Auth** という種類のクレデンシャルを新しく作成します。これはn8nに最初から組み込まれている汎用的なクレデンシャルで、`Authorization: Bearer ...` ヘッダーを送信するために特別に設計されています。設定フィールドは1つだけです：

```
Bearer Token: YOUR_API_KEY
```

Bearer Tokenフィールドの横にある小さな `fx`（または `=`）トグルをクリックして、入力を「式（Expression）モード」へと切り替えます。そして、その値をフォームの入力への参照へと置き換えます：

```
Bearer Token: ={{ $('On form submission').item.json.api_key }}
```

先頭の `=` プレフィックスは、これが文字列のリテラルではなく「式」であることをn8nに伝えます。`{{ }}` の内側はすべてJavaScriptであり、`$('Node Name').item.json.field` はワークフロー全体を越えて他のノードから値を取得するための長い記述形式（ロングフォーム）の参照です。これは、[Implementation notes #001](https://dev.to/hidekimori/build-a-multi-step-n8n-form-with-dynamic-dropdowns-no-plugin-needed-1pm4) で解説したパターンと全く同じです。Bearer Authクレデンシャルは、リクエスト送信時に自動的にトークンの前に `Bearer ` を付与してくれるため、自分でプレフィックスを記述する必要はありません。

クレデンシャルを保存すると、次のようなメッセージが表示されます：

```
[ERROR: No path back to node]
```

これは表示上のエラーに過ぎません。クレデンシャルの編集画面には、現在実行中のワークフローのコンテキスト（実行状態）が存在しないため、その瞬間には式を解決できないのが原因です。後からワークフローの実行中にHTTPノードがこのクレデンシャルを呼び出したときには、式は正しく解決されます。

![Bearer Auth credential with expression mode](https://static.zenn.studio/user-upload/2c4b5feb9cd9-20260524.png)

多くの人がここで設定を諦めてしまうため、ここは少し立ち止まって確認する価値があります。彼らはクレデンシャルが壊れていると思い込み、この手法を捨ててしまいます。しかし、壊れてはいません。構わず保存してください。ワークフローを実行すれば、キーは正しく流れ始めます。

> **エラーテキストに関する注意：** クレデンシャルの種類によって、同じ状況でも表示されるメッセージの文言がわずかに異なります。Bearer Authクレデンシャルでは `[ERROR: No path back to node]` と表示されますが、一部のカスタムノードのクレデンシャルでは `[ERROR: Referenced node doesn't exist]` と表示されることがあります。根本的な原因（編集時にはワークフローのコンテキストがないこと）と、実行時には無害であるという事実は全く同じですが、クレデンシルの実装によって文言が異なるだけです。

> **クレデンシャル種類の選択に関する注意：** Bearer Authは、標準的な `Authorization` ヘッダーを使用します。もし対象のAPIが、`X-API-Key` や `X-Custom-Auth` といった異なるヘッダー名を期待している場合は、代わりに **Header Auth**（カスタムの名前/値）や **Custom Auth**（フルJSON形式のヘッダー）を使用してください。式モードを使用したテクニックは、どれを使っても全く同じように動作します。

## HTTPノードでクレデンシャルを使用する

HTTP Requestノードを、先ほど作成したクレデンシャルを使用するように構成します：

```
HTTP Request
  Authentication:    Generic Credential Type
  Generic Auth Type: Bearer Auth
  Credential:        <作成したクレデンシャルの名前>
  Method:            (APIが要求するメソッド)
  URL:               (エンドポイント)
```

これで、HTTPノードはフォームから入力された値を含んだ `Authorization: Bearer ...` ヘッダーを送信するようになります。コード内へのキーのハードコードも、ユーザーごとの個別なクレデンシャル設定の手間もありません。ワークフローがフォームで問いかけ、ユーザーが入力し、リクエストが送信されます。

ワークフローが必要とする数だけ、いくらでもHTTPノードを配置することができます。それらすべてのノードが同じクレデンシャルを参照するため、下流でどれだけ多くのエンドポイントが呼び出されようとも、ユーザーがフォームに入力する回数は最初の1回だけで済みます。

## 代替案：クレデンシャルを完全にスキップする

ワークフローに含まれるHTTPノードが1つだけの場合、このプロセスをショートカットすることができます。HTTPノードの `Authentication` を `None` に設定し、ヘッダーを直接記述する方法です：

```
HTTP Request
  Authentication: None
  Headers:
    - Name:  Authorization
    - Value: =Bearer {{ $('On form submission').item.json.api_key }}
```

この方法でも正しく動作します。設定にかかる時間は短いため、知っておく価値はあります。

ただし、この方法では以下のメリットが得られません：

- 同一ワークフロー内の複数のHTTPノードでの認証情報の再利用
- クレデンシャルを前提として設計されているカスタムノードへの接続経路（これについては後述します）
- 「これは認証情報である」という枠組みと「これはリクエストデータである」という枠組みの精神的な分離

この代替案は、一回限りのプロトタイプを作る際にとどめておくべきです。複数の認証呼び出しを含む、一般に公開するテンプレートの場合、クレデンシャルを使用したアプローチの方が美しくスケールします。

## 注意すべき3つのこと

### 1. 表示上のエラーはクレデンシャルの種類によって文言が異なる

前述した通り、クレデンシャルの編集画面には実行コンテキストが存在しないため、設計時には式を解決できません。保存して、ワークフローを実行すれば解決されます。ここで留意すべきは、**メッセージ自体がクレデンシャルの種類によって異なる**という点です：

- Bearer Auth、Header Auth、およびほとんどの汎用クレデンシャル： `[ERROR: No path back to node]`
- 一部のカスタムノードのクレデンシャル（例として、後述するLDX hubのDynamicクレデンシャルなど）： `[ERROR: Referenced node doesn't exist]`

どちらも設計時の表示上のエラーに過ぎず、実行時には消失します。文言の違いに惑わされて、片方のクレデンシャルがもう片方より致命的に壊れていると思い込まないでください。

なお、式の中に文字通りタイポ（参照するノード名の誤りなど）がある場合も、設計時には全く同じエラーメッセージが表示されます。表示上のエラーなのか、本当のタイポなのかを区別する唯一の方法は、ワークフローを実際に実行し、送信されるリクエストのログを確認することです。

### 2. `Password` エレメントタイプが制御するのはマスキングであり、セキュリティではない

Form Triggerの `Password` エレメントタイプは、画面上の入力を隠す（マスクする）だけです。データを暗号化するわけでも、キーを特別な安全領域に隔離して保存するわけでもなく、n8nの実行ログ（Execution logs）からキーを隠蔽するわけでもありません。ワークフローの実行履歴にアクセスできる人間であれば、誰でも送信された未加工のキーを確認することができます。

画面上のマスキングは、ユーザーに対する「背後からの覗き見を防ぐための配慮（礼儀）」であり、厳密なセキュリティ境界ではないと理解してください。もしより強力なセキュリティの保証が必要な場合、キーは適切に暗号化されて保管された環境（クレデンシャル管理画面）に置かれる必要がありますが、その時点でユーザーごとの個別設定が必要になり、フォームベースの簡便さというメリットは失われてしまいます。

このパターンは「利便性の最適化（UXの向上）」を指向したものであり、厳密な「シークレット管理」を指向したものではありません。外部のボルト（Vault）の統合や、監査ログ、キーのローテーションといった本質的なシークレット処理が必要な場合、n8nはEnterpriseプランで外部Vaultのサポートを提供しています。それ以外のユースケースにおいて、このフォームベースのパターンはUXの最適化であって、セキュリティのアップグレードではないことを念頭に置いてください。

### 3. クレデンシャルはグローバルであり、式はランタイムスコープである

このパターンの背景には、少し奇妙な構造上の事実があります。クレデンシャルのレコード自体は、特定のワークフローに紐付いていません。n8nはクレデンシャルをグローバルに保存し、あらゆるワークフローがそれを参照できます。しかし、クレデンシルの内部にある「式」は、名前によって特定のノード（`$('On form submission')`）を参照しており、これはワークフローの実行コンテキストの内部でしか解決できません。

クレデンシャルはグローバルであるのに対し、その中にある式はワークフロー内に閉じている（ランタイムスコープである）。編集時には、これら2つの世界は切り離されています。実行時になって初めて、n8nはそれらを結びつけますが、それは「両者の名前が完全に一致している場合」に限られます。

これこそが、あるテンプレートのノード名に基づいて構築されたクレデンシャルが、そのノードを持たない別のワークフローで使われたときにエラーを引き起こす理由です。このミスマッチは、ワークフローを実行する瞬間まで静かに潜伏しています。

対策としては、テンプレート間でトリガーノードの名前を統一するか（常に `On form submission` にするなど）、あるいはテンプレートごとに個別のクレデンシャルレコードを作成することです。APIキーを求める複数のテンプレートを配布する場合、長期的な運用を考えると「テンプレートごとに1つのクレデンシャルを作成する」方がすっきりとした形になります。クレデンシャルレコードの作成コストは安価ですが、名前のミスマッチが引き起こすコストは高くつくからです。

## カスタムノードが「式モードのクレデンシャル」をサポートする場合

動的クレデンシャルに関する議論の多くは、前述したHTTPノードのパターンで終わりがちです。しかし、もう一つの重要なクラスが存在します。独自のクレデンシャルタイプを定義している、コミュニティ製のカスタムノード（`n8n-nodes-asana` や `n8n-nodes-ldxhub` など）です。これらはHTTPノードのヘッダーを直接触るのではなく、クレデンシャルから直接値を読み取ります。つまり、「フォームからクレデンシャルへ値を渡す」パターンを、ノード自体のスキーマが許容していなければなりません。

多様なユースケースを想定して設計されているカスタムノードは、ユーザーが同じクレデンシャルの中で2つのモードを選択できるようにしています：

**Static モード** —— 従来のクレデンシャルのセットアップ：

- キーがクレデンシャルレコードに直接ハードコードされて保存される
- ユーザーまたはインスタンスごとに1回限りのセットアップを行う
- ワークフローの運用者自身が、自分自身のアカウントに対してワークフローを実行する一般的なケースに適している

![LDX hub Static credential](https://static.zenn.studio/user-upload/8cfd458e2f13-20260524.png)

**Dynamic モード** —— 同じクレデンシャルタイプで、キーのフィールドを「式モード」に切り替えた状態（`={{ $('On form submission').item.json.api_key }}`）：

- キーは実行時にフォームの入力から動的に解決される
- ユーザーごとの事前のセットアップが不要
- 他の人に配布するためのテンプレートに適している

![LDX hub Dynamic credential](https://static.zenn.studio/user-upload/53cbf724daa0-20260524.png)

全く同じクレデンシャルタイプですが、2つの利用パターンが存在します。ユーザーは自分が何をしようとしているかに基づいて、モードを選択することができます。

> なお、ここで式モードになっているのはAPI Keyフィールドだけであり、Base URLは静的な `https://gw.ldxhub.io` のまま残されています。もちろんBase URLも式モードにすることは可能であり、LDX hubパッケージに含まれる `all-services-demo` テンプレートでは、実際にフォーム上でホスト名をユーザーに問いかける設計にしています。ただ、この記事の例では、動く部分を1つ（式を1つ）に絞ってシンプルに保っています。

ノードの開発者にとっての教訓は、「最初から式モードの値を許容するようにクレデンシャルスキーマを設計しておくこと」です。`{{ }}` の構文を拒絶するような厳格な正規表現（RegEx）バリデーションをハードコードしてはいけません。また、初期値が空であるからといって、クレデンシャルの保存時にエラーを吐かないようにしてください（式が解決されるのは実行時であり、保存時ではないためです）。値が他の場所から計算されて流れてくる可能性を排除しないことが大切です。

両方のモードで動作するノードは、クレデンシャルのフィールドで式を有効にするという「わずかな投資」だけで、個人用の自動化とテンプレート配布という、2倍のコンテキストで役立つようになります。これは、非常に費用対効果の高いアプローチです。

## なぜこれが重要なのか

デフォルトのn8nワークフローは、「単一のアカウント」に依存したものです。作成者は自分自身のクレデンシャルを使ってAPIを呼び出すように構築して保存し、それは作成者の元で動き続けます。それをインポートした他の誰かは、アカウント環境を完全に一致させるか、あるいは認証部分を手動で書き直す必要があります。

動的クレデンシャルは、その前提を覆します。同じワークフローが、それを実行する人（彼らのAPIキー、彼らのアカウント、彼らの利用料）に柔軟に適応するようになります。テンプレートは、個人の成果物から、誰でもインポートしてすぐに使える「小さなアプリケーション」へと姿を変えるのです。

動的ドロップダウン（[Implementation notes #001](https://dev.to/hidekimori/build-a-multi-step-n8n-form-with-dynamic-dropdowns-no-plugin-needed-1pm4)）と組み合わせることで、これが「本当に配布可能なワークフロー」を出荷するために必要な2つ目のピースとなります。フォームがキーを求め、クレデンシャルがそれを繋ぎ、HTTPノード（または対応するカスタムノード）がリクエストを飛ばす。設定のための儀式も、アカウントのジャグリングも、設定ページから設定ページへと認証情報をコピー＆ペーストする不毛な作業も、そこには一切存在しません。

## 完全なリファレンス・ワークフロー

[n8n-nodes-ldxhub](https://www.npmjs.com/package/n8n-nodes-ldxhub) パッケージに含まれる `all-services-demo` の例には、このパターンが組み込まれています。Form TriggerがAPIキーとホスト名を求め、動的クレデンシャルがそれら両方を5つの異なるサービスパスへと受け渡し、それぞれのパスでは式モードのクレデンシャルを備えたLDX hubカスタムノードが使用されています。クレデンシャルの構成と、それを消費するノードの呼び出しの実態を確認したい場合は、`examples/all-services-demo.json` をインポートして調べてみてください。

デモを実行するための無料のLDX hubキーが必要な場合は、[gw.portal.ldxhub.io](https://gw.portal.ldxhub.io) で取得できます（月間25,000クレジット、クレジットカード不要）。あるいは、このクレデンシャルのパターンだけを拝借して、あなたが望む任意のAPIに適用してみてください。

## 終わりに

クレデンシャルで式を使用するパターンは、n8nの設計思想として完全に認められているテクニックでありながら、「これがテンプレートを配布するための王道レシピだ」としては、なぜかこれまで十分にドキュメント化されてこなかったものの一つです。それはただ、すべてのクレデンシャルフィールドの横にある小さな `fx` トグルとして、誰かがそれをオンにするのを静かに待ち続けていました。

ノードの開発者にとって、最初から式モードを考慮した設計をしておくコストは、ほぼゼロに近いものです。そしてワークフローの作成者にとって、このテクニックを採用するか否かは、「これを使うために4つの設定手順を踏んでください」とユーザーに要求するか、「このフォームにあなたのキーを貼り付けてください」とだけ伝えるかという、決定的なUXの差を生み出します。

この記事の最も「退屈」な点は、突飛なハックは何一つ起きていないということです。n8nには、最初からそのメカニズムが備わっていました。足りなかった唯一のピースは、**「クレデンシャルは、必ずしもワークフローの作成者のものである必要はない」** というパラダイムシフトに気づくこと、それだけだったのです。
