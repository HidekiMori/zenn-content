4 月 15 日から 4 月 30 日まで。2 週間。1 人。そこに AI が加わった。

これはライブレポートで、振り返りではない。

このシリーズのこれまでの記事は、形 (shape) についての話だった。契約、パターン、24 年 1 人で書いてきたこと。今回は、その形に AI を加えた時に何が起きたか、そして速度がどう変わったか、の話。

今もまだその中にいながら書いている。形は保たれた。速度は変わった。

---

## 2 週間でやったこと

2 週間、1 人。淡々と並べる:

- **API ゲートウェイ**: Zuplo、5 つのサービスを 1 つの公開 API の下に統合
- **カスタムドメイン**: 本番は `gw.ldxhub.io`、デベロッパーポータルは `gw.portal.ldxhub.io`
- **DevPortal**: API リファレンスを自動生成、加えて introduction、サービス別ガイド、価格、MCP セットアップ、"use anywhere"
- **認証**: Auth0 で Google OAuth、GitHub OAuth、メール — サインアップから最初の API コールまで約 30 秒
- **Free プラン**: 月 25,000 クレジット、クレジットカード不要
- **課金**: クレジット制で統一、1 クレジット $0.0001、4 プラン (Free / Starter $15 / Standard $50 / Pro $150)、超過は同じレート
- **Stripe 連携**: 有料プランのサブスクリプションと超過分の決済に接続
- **非同期メータリングパイプライン**: ジョブ完了 *後* (`202 Accepted` から数分以上経ってから) にクレジット消費を発火させる別経路、ゲートウェイの billing API にバッチで送る
- **5 サービス公開**: StructFlow、RefineLoop、RenderOCR、CastDoc、ExtractDoc
- **4 チャネル統合**: n8n ノード (verified、マーケットプレイス公開済)、Dify プラグイン (verified、多言語)、Claude Desktop のような AI アシスタント向け MCP、加えて直接 API
- **マーケティングページ**: コーポレート LP (`ldxlab.io/ldxhub`、加えてサービス別ページ) に 4 つの製品ページ、それぞれが developer portal にリンク
- **dev.to と Zenn で 8 本の予約記事**、設計哲学を書いている。この記事はその 5 本目。

これは表面。どれも派手じゃない。どれも必要だった。

---

## 形は保たれた

過去の記事で書いてきた形は変わらなかった。

ジョブが入る。API が仕事を抱える。API が必要な分だけリトライする。報告できる結果が出たら API が報告する。2003 年に音楽配信プラットフォームを動かし、2006 年から 2014 年まで電子書籍プラットフォームを動かしたのと同じ形が、今は構造化抽出サービスと、その他 4 つを包んでいる。

変わったのは、その中の速度だった。

---

## 速くなったもの、変わらなかったもの

**速くなったもの:**

- API 設計のイテレーション — どのインターフェースも 3〜4 通りの形を経て落ち着いた
- 4 言語のドキュメント (英語、日本語、中国語、ポルトガル語) — マーケットプレイスのプラグインで必要で、順番にやってる時間がなかった
- エッジケースの言語化 — 「`inputs` と `file_id` の両方がない場合どうなるか?」のような問いを、出た時間のうちに文章で答える
- マーケットプレイスプラグインのオンボーディング (n8n、Dify) — 提出、レビュー、バージョン更新
- マイグレーション、フィクスチャ、動作確認

**変わらなかったもの:**

- 課金構造の判断
- 統合の境界をどこに引くか (どのエンジンを使うか、どの表面を出すか)
- 何を出すか、何をスキップするか
- 何をレガシーの内部 API に残し、何を公開サービスにするか

AI は判断を置き換えなかった。タイピングをほぼ置き換えた。

(ほぼ、と書いた。公開サービスとレガシー内部 API を繋ぐラッパーは、自分でタイプした。小さくて、boring で、24 年やってきて頭の中にすでにあった形そのものだった。説明するよりタイプした方が速い。)

---

## 一番難しかったこと

諦めかけたのは、非同期ジョブのクレジットメータリングだった。

ほとんどの API ゲートウェイはリクエスト単位でメータリングする — 簡単。私が必要だったのは、ジョブが *完了した時* にメータリングすること。`202 Accepted` を返してから数分後 (もっと長い場合もある) のタイミングだ。

2 つのゲートウェイを評価した。どちらも書面上は非同期レポーティングができた。1 つ目は最後まで通した — API もある、ドキュメントもある、でも UI と運用挙動にどうしても無視できない粗さがあった。私は 2 つ目を使いたかった。だから戻った。

2 つ目のゲートウェイが、私の着地点だった。ただ、辿り着いた時、必要としていた非同期メータリングが本当に可能かどうかが分からなかった。ドキュメントはちょうどその部分が薄かった。サポートボットを試した。ボットも知らなかった。そこに人間が現れて、ジョブ完了側からメータリングイベントをバッチで発火する方法を案内してくれた。

動いた。

この構築の中で、向こう側の誰かに「できる」と確認してもらうまで実現可能性が分からなかった、唯一の部分だった。これは覚えておきたい。24 年 1 人で書いてきて、この未知への最短経路は、自分で解くことではなかった — 訊くことと、向こう側がちゃんと答えてくれることだった。

(Stripe でも小さい引っかかりがあった。ゲートウェイの課金フローを動かすために Stripe 側で何かを設定する必要があると思い込んでいた。その「何か」を探すのに少し時間を使った。なかった。ゲートウェイが端から端までやっていて、Stripe は受け取るものを受け取るだけだった。「これをどう統合すればいい?」の答えが「もう統合されている」になることが、たまにある。)

---

## 判断の総量

ここが驚いた部分。

アウトプットが劇的に増えた。これは予想していた。予想していなかったのは、判断と分岐の総量も同じだけ増えたこと。1 つずつ閉じていくしかない — 回避策はない。それぞれの判断を閉じるのも速くなったので、どれもボトルネックにはならなかった。

でも疲労の質が違う。

24 年 1 人で作ってきた。疲れがどんなものかは知っている。これはまた別物だ。速度がすべてを圧縮する — 問い、答え、小さな軌道修正 — どれも落ち着く時間のない窓の中に。フェーズの中にはいない。常につなぎ目にいる。

24 年の 1 人作業から予想していなかったこと: 分岐を見逃すことを心配したことはなかった。判断の総量は、いつも 1 つの頭で抱えられる範囲に収まっていた。今は、アウトプットが倍化したことで、新しい恐れがある — 5 つ別のことを閉じている間に、考慮すべきだった何かが通り過ぎてしまったのではないか、という恐れ。道は動き続け、隣接する分岐は広がり続け、コミットする前に全部見たい。その恐れは前はなかった。麻痺するほどじゃない。ただ、ある。

これにどう対処するか、明確な答えはない。これは大事に思えるし、私が読んだ AI ツールの記事には書かれていないから、報告として記しておく。

---

## 理論ではなく、削除

ここは残しておきたい部分。

この速度では、理論化はしない。削除する。

すべての選択肢をモデル化したり、会議でトレードオフを天秤にかけたり、デックを作ったりする時間はない。あるものを 1 時間手に持って、次のものとの接触に耐えるかを見て、残すか取り除く。残るのは、議論する時間がなかったものだ。

これは生産性の主張ではない。記述だ。

friction が十分に低くなった時 — タイピングがレートリミッターでなくなった時 — 判断のされ方が変わる。判断は、何かが可能にするかではなく、何かが支えられないか、で行われる。否定形のケースの方が肯定形のケースより大きくなる。「これを足したらどうか?」を訊くのをやめて、「これは後で取り除きにくくなるか?」を訊くようになる。

これが一般化するかは分からない。この 2 週間で起きたこと、それは分かる。

---

## Closing

速度は美徳ではない。friction がなくなった時に起きること、それだけ。24 年経って、私に残っていた friction はほとんどタイピングだった。

タイピングを取り除いた。形はすでにあった。

疲労もまた、レポートの一部だ。
