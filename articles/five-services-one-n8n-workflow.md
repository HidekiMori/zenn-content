このシリーズの最初の2つの記事では、それぞれ1つのテクニックを紹介しました。[Implementation notes #001](https://zenn.dev/hidekimori/articles/n8n-dynamic-dropdowns) は動的ドロップダウン、つまりAPIから自動的に中身が埋まるフォームフィールドでした。[Implementation notes #002](https://zenn.dev/hidekimori/articles/n8n-dynamic-credentials) は動的クレデンシャル、つまりフォームから入力されたAPIキーを裏側でHTTPノードへと受け渡す仕組みでした。

この記事は、その集大成（Capstone）です。`n8n-nodes-ldxhub` パッケージに同梱されているサンプルワークフロー `all-services-demo` を紐解きながら、これら2つのテクニックがSwitchノードとどのように組み合わさり、5つの異なるAIドキュメント処理サービス（構造化抽出、翻訳推敲、OCR、PDF変換、テキスト抽出）を1つのワークフロー内に同居させているのかを解説します。

> 以下のスクリーンショットとワークフローのJSONは、`n8n-nodes-ldxhub` パッケージからのものです。ここで使われているパターン自体は汎用的なものであり、単一のテンプレートに統合したい任意のサービスの組み合わせに対して機能します。

この記事は「この手順に従ってください」というチュートリアルではありません。これは部品のカタログです。まったく同じ問題を抱えている読者は二人といませんし、テンプレートが誰かの状況にそのままぴったりと当てはまることは稀です。あなたの用途に合うものだけを持ち帰り、残りは捨ててください。パターンを再利用するために、46個のノードすべてを理解する必要はありません。

## 全体像（The shape）

このワークフローは46個のノードを持っています。エディタ上で見ると威圧感を与えるのに十分な数ですが、構造的に言えば単に5つの反復するパスと、小さなルーティングセクションがあるだけです。

![all-services-demo workflow overview](https://static.zenn.studio/user-upload/3ca575b2ab48-20260525.png)

入り口となるセクションは2つのノードで構成されています：

- **On form submission** — トリガーです。ユーザーにどのサービスを利用したいかを尋ね、APIキーを収集します。
- **Route by Service** — サービスごとに1つ、計5つの出力を持つSwitchノードです。

Switchノードから右側にあるものはすべて、特定のサービス専用のものです。StructFlow、RefineLoop、RenderOCR、CastDoc、ExtractDocという5つのパスが扇状に広がっています。それぞれのパスは、2つのForm Endingノード（成功時に結果を自動ダウンロードするものと、エラーを表示するもの）で終わります。

これが背骨（Spine）です：フォーム → スイッチ → サービスパス → エンディング。複雑さは、各サービスパスの内側に押し込まれています。

## 背骨：静的な比較によるルーティング

Switchノード（"Route by Service"）は、Rulesモードを使用しています。各ルールは、フォームから渡された同じ式（`{{ $json.service }}`）を読み取り、それを静的なサービス名と比較します。

![Switch node Route by Service](https://static.zenn.studio/user-upload/011977c25211-20260525.png)

```
Rule 1:  {{ $json.service }}  is equal to  structflow   → output: structflow
Rule 2:  {{ $json.service }}  is equal to  refineloop   → output: refineloop
Rule 3:  {{ $json.service }}  is equal to  renderocr    → output: renderocr
Rule 4:  {{ $json.service }}  is equal to  castdoc      → output: castdoc
Rule 5:  {{ $json.service }}  is equal to  extractdoc   → output: extractdoc
```

読み取り側は動的です（式はユーザーが選んだものに解決されます）。一方、照合側は静的です（固定の文字列）。この非対称性は意図的なものです。ルールが静的であるということは、新しいサービスを追加する際には手動での編集が必要になることを意味します。Switchノードを開き、行を追加し、保存する。自動生成も、テンプレートフックも、自動検出もありません。退屈で、何の驚きもありません。

この部分は、そのままきれいに持ち帰ることができます。上流からの1つの式によって駆動する、N個の静的ルールを持つSwitchノード。これはサービスのルーティング、ドキュメントタイプのルーティング、ユーザー層（Tier）のルーティングなど、個別のブランチにファンアウトするあらゆるものに機能します。

## 内部にある2つのパターン

サービスパスを読み解き始めると、あることに気づくはずです。それらはすべて同じ形をしているわけではありません。そこには2つの明確に異なるパターンが存在します。

### パターンA：単一ステップのフォーム（StructFlow, RefineLoop — 7ノード）

```
Get Models (HTTP)
  → Derive Options (Set)
    → Run Form (Form, next page)
      → Inject Binary (Code)
        → Run (LDX hub)
          → Download / Error (Form Endings)
```

![StructFlow path](https://static.zenn.studio/user-upload/e54bb78e16d4-20260525.png)

1つのフォームページが、ユーザーが選択すべきすべてを収集します。モデルの選択、入力データ、パラメータ。それらがすべて1つの画面に収まっています。Switchノードの後に存在するフォームページは1つだけです。

### パターンB：カスケードするマルチステップのフォーム（RenderOCR, CastDoc, ExtractDoc — 10ノード）

```
Get Engines (HTTP)
  → Select Engine (Form, next page)
    → Derive Options (Set)
      → Upload File (Form, next page)
        → Filter by File (Set)
          → Select Output (Form, next page)
            → Inject Binary (Code)
              → Run (LDX hub)
                → Download / Error (Form Endings)
```

![RenderOCR path](https://static.zenn.studio/user-upload/27f85dd97559-20260525.png)

3つのフォームページがあり、それぞれが前のページの結果によって制限（ゲート）されています。最初にエンジンを選択します。次にファイルをアップロードします。そして最後に出力フォーマットを選択しますが、ここで利用可能な出力フォーマットは「選ばれたエンジンが、アップロードされたファイルタイプに対して何をサポートしているか」に基づいてフィルタリングされます。`Filter by File` というSetノードが、その依存関係の真ん中に置かれています。

### なぜ1つではなく、2つのパターンなのか

パスの形は、ユーザーが意思決定を行う形に従っています。選択が独立している場合（モデルを選び、データを渡すだけの場合）は、1つのフォームページで十分です。選択がカスケードする場合（エンジンがファイルタイプを制限し、ファイルが出力フォーマットを制限する場合）は、フォームを分割し、中間のSetノードがページ間で選択肢をフィルタリングしなければなりません。

私は当初、5つのサービスすべてに単一のパターンを強制しようと試みました。しかしそれは、シンプルなサービスを必要以上に複雑にするだけでした。誠実な設計とは、カスケードするサービスは長いままにし、その非対称性を受け入れ、それをドキュメント化することでした。

2つのパターンが存在することは、不完全さの表れではありません。2つの異なる形が純粋に必要であったことを、統合のプロセスが受け入れた結果です。

## 1つのパスの解剖学

StructFlowのパスを歩くことで、5つのパスすべてに共通する語彙を得ることができます。残りの4つは、そのバリエーションに過ぎません。

**Get Models** — `/structflow/models` を叩き、利用可能なLLM（gpt-5.5, claude-sonnet-4-6, gemini-3-flashなど）を返すHTTPノードです。これがドロップダウンのデータソースになります。

**Derive Options** — モデルのリストを、n8nのForm Triggerがドロップダウンとして期待するフォーマット（`[{name, value}, ...]`）に整形するSetノードです。[#001](https://zenn.dev/hidekimori/articles/n8n-dynamic-dropdowns) で紹介したのと同じトリックです。ドロップダウンの選択肢はハードコードするのではなく、データから導出します。

**Run Form** — 使用するモデル、入力データ、パラメータなど、すべての情報を尋ねる単一のフォームページです。「model」ドロップダウンは、上流の `Derive Options` ノードから選択肢を読み取ります。

**Inject Binary** — 1つの仕事だけをするCodeノードです。n8nにおいて、アップロードされたファイルは `json` フィールドとは分離された `binary` データとしてワークフロー内を移動しますが、一部の中間ノード（Setなど）はJSON側しか保持しません。データがLDX hubノードに到達する頃には、バイナリ部分は欠落してしまっています。

```javascript
return $input.all().map(item => ({
  json: item.json,
  binary: $('StructFlow: Run Form').item.binary
}));
```

このCodeノードは、フォームノードまで遡ってバイナリを再びアタッチします。たった1行の糊（glue）ですが、これがなければファイルは消え去ってしまいます。

**Run** — `runJob: structFlow` が設定されたLDX hubのカスタムノードです。ここで実際にAPI呼び出しが行われます。クレデンシャルは式（Expression）モードに設定されており、フォームの入力から読み取るようになっています。これは [#002](https://zenn.dev/hidekimori/articles/n8n-dynamic-credentials) の動的クレデンシャルのパターンです。

**Download / Error** — 2つのForm Endingノードです。Runノードには2つの出力ポートがあります。Success（成功）はDownload（結果ファイルを提供する）へ、Error（エラー）はError（エラーメッセージを表示する）へと進みます。

他の5つのパスも、基本的には同じアイデアに従っています。名前が変わり、フォームページの数が変わるだけで、各ノードの役割は同じです。

## 収束：5つのパス、1つのノード

5つのサービスパスはすべて、同じLDX hubカスタムノードに行き着きます。同じノードタイプ、同じクレデンシャル、同じ形。唯一異なるのは `runJob` パラメータだけです：

| サービスパス | 設定パラメータ |
|---|---|
| StructFlow | `runJob: structFlow` |
| RefineLoop | `runJob: refineLoop` |
| RenderOCR | `runJob: renderOcr` |
| CastDoc | `runJob: castDoc` |
| ExtractDoc | `runJob: extractDoc` |

これがカスタムノードの提供する抽象化です。ワークフローの視点から見れば、「サービスを実行する」という振る舞いは、5つのパス全体で完全に同一に見えます。その違いはノードの実装の奥深くに埋め込まれており、本来あるべき場所に収まっています。

これは、[#002のサイドバー](https://zenn.dev/hidekimori/articles/n8n-dynamic-credentials) で触れたアイデアを一般化したものです。バリエーションを統一されたインターフェースの背後に隠すカスタムノードは、自由な構成（コンポジション）を可能にします。

Five services. One credential type. One node. Five jobs.

ワークフローの作成者は、StructFlowがRenderOCRとどう違うのかを知る必要はありません。ノードがそれを知っています。

もしあなたが独自のカスタムノードを構築しようとしているなら、これは目指す価値のある形です。ジョブの種類によってパラメータ化される、単一のノード。ワークフローはクリーンに保たれ、バリエーションはノード内にカプセル化されます。

## if/elseのペア：エラーエンディング

すべてのサービスパスには、Download（成功）とError（エラー）という2つの終着点があります。どちらもForm Endingノードであり、どちらもユーザーの目に触れるものです。これは単なる装飾ではありません。

配布可能なテンプレートには、1つの最低限の義務があります。それは、ユーザーが「Submit（送信）」をクリックした以上、彼らに「何が起きたのか」を示す必要があるということです。呼び出しが成功したなら、結果を得る。失敗したなら、エラーを得る。フォームがただ無言で終了する「第3の状態」は存在してはなりません。

もっと早い段階での失敗（Get Modelsの呼び出しが空を返す、Inject Binaryノードがクラッシュするなど）は、ここでは処理されていません。テンプレートは最小限であるべきであり、至る所にエラーエンディングを追加するとキャンバスが読めなくなるため、それらは省略されています。しかし、最後のRunノードのエラーブランチは必須です。そこは、ユーザーの「ジョブを開始したけれど、何が起きた？」という期待に対して、必ず答えを返さなければならない唯一の場所だからです。

`if` があるところには、`else` が必要です。`else` はエレガントである必要はありません。ただ存在していればいいのです。

この部分は、単独で持ち帰ることができます。ワークフローにユーザーの目に触れる「実行（Run）」ステップがあるときはいつでも、その成功とエラーのエンディングをペアにしてください。他のブランチは省略したりログに記録したりしても構いませんが、ユーザーに面しているブランチだけは交渉の余地がありません。

## 統合するということ

ここまで紹介したテクニックの部品（Switchルーティング、2つのフォームパターン、バイナリの注入、Runノードへの収束、if/elseエラーのペア）は、それぞれが持ち運び可能な（ポータブルな）ものです。一つずつ切り取って使うことができます。しかし、この記事がそこで終わってしまっては、何かが欠けていることになります。

5つのサービスを1つのワークフローに持ち込むこと自体が、1つの「仕事」なのです。このセクションで語る内容は独立したテクニックではないため、チュートリアル向きの仕事ではありません。それは、小さな決断の連続です：

- どの5つのサービスを含めるかを選ぶ（すべてではない。デモとしては5つで十分であり、それ以上はノイズになる）。
- パス全体でノードの命名規則を標準化する（どこでも `<Service>: <Role>` にする。そうすれば、読者は自分がどこにいるのかを常に把握できる）。
- 2つのパターンが実在することを受け入れ、すべてのパスを無理に同じ形に押し込めない。
- 違いはフォームページの内側と、Runノードの `runJob` パラメータの内側に押し込む。背骨（Spine）は均一に保つ。
- 収束を設計する。すべてのパスが同じノードタイプで終わるようにすることで、後から6つ目のサービスを追加する作業は「再設計」ではなく「コピペと編集」になる。

これらのどれも、決して賢い（巧妙な）ものではありません。代替案を見れば、どれも当たり前の決断です。しかし、その当たり前の決断こそが、テンプレートを一つにまとめているのです。

この記事は、特定の種類の読者のためにも書かれています。つまり、テクニック自体は必要としておらず、単にn8nにドロップしてすぐに動かせる「実用的なテンプレート」を必要としている読者です。その統合という仕事こそが、彼らにとっての成果物（Deliverable）です。この記事がその仕組みをも解説しているというのは、副次的な恩恵に過ぎません。

これは、関心事をそれぞれ狭い責任を持つ複数の個別のサブワークフローに分散させるという、別の設計哲学とは対照的です。複数のメンテナーを抱える大規模なn8n環境であれば、これらの責任を再利用可能なサブワークフローに分割し、各サービスをExecute Workflowノード経由で呼び出すのが良いかもしれません。しかし、持ち出されて適応されることを意図した「単独でメンテナンスされる配布可能なテンプレート」においては、統合された形の方が理解しやすく、出荷しやすいのです。動く部品が少なく、統合ポイントが少なく、読むべき場所が1つで済みます。

## 終わりに

これは部品です。

もしあなたがこの記事を読み、ワークフロー全体を持ち帰ってそのまま動かすのなら、それで構いません。もしSwitchノードのルーティングだけを持ち帰り、すべてのサービスパスをゼロから再構築するのなら、多くの場合その方が良いでしょう。もし、昨日あなたを苦しめたのがバイナリの消失だったからという理由で、Inject Binaryのトリックだけを持ち帰り、それがこの記事の最も優れた使い方です。

まったく同じ要件というものは存在しません。すべての読者は、異なる問題を解決しようとしています。「これが万能の答えだ」と振る舞うテンプレートは、嘘をついていることになります。そうではなく、「これは部品のカタログである。ここにピースがあり、これらはこう組み合わさる。合うものだけを持ち帰ってほしい」と正直に提示するテンプレートは、また別の種類の実用性を持っています。

それが `all-services-demo` の目指したものであり、この記事が目指したものです。

[n8n-nodes-ldxhub パッケージ](https://www.npmjs.com/package/n8n-nodes-ldxhub) には、ノードのコードと一緒に `examples/all-services-demo.json` が同梱されています。これをあなたのn8nインスタンスにインポートし、[LDX hubのAPIキー](https://gw.portal.ldxhub.io)（無料枠: 月間25,000クレジット、クレジットカード不要）を追加すれば、ワークフローは動きます。JSONを開いて、部品をあなた自身のテンプレートに持ち帰ってください。

これで「Implementation notes」の第1フェーズを閉じます。3つの記事で、同じテーマ（いかにしてn8nワークフローを、小さく配布可能なものにするか）を3つの角度から捉えました。次のフェーズでは、また別の書き残す価値のある領域を取り上げる予定です。
