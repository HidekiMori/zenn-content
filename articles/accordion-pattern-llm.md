![](https://static.zenn.studio/user-upload/0c34469a0dcd-20260502.png)
構造化抽出のチュートリアルって、だいたい同じ形をしています。ドキュメントを渡して、「A、B、C、D、E、F を抽出して」という大きなプロンプトをひとつ書いて、JSON を受け取る。これで完成。

短い入力に対しては、これで動きます。

長い入力では、静かに壊れます。

本番で運用してみて、私はこのやり方をやめました。何に切り替えたか、なぜ切り替えたかを書いておきます。

---

## 太ったプロンプトの問題

50 ページのレポートから構造化サマリを得たいとします。最初にやりたくなるのはこんな感じ。

```
以下を抽出してください:
- title
- sections (見出し付き)
- purpose
- mentioned services
- acceptance criteria
- ...
このスキーマで JSON を返してください: { ... }
```

ドキュメント全体をモデルに渡し、JSON が返ってきます。最初は問題なさそうに見えます。

ところがスケールさせると、3 つのことが起きます。

1. **品質がぶれます。** モデルがドキュメントの途中で「忘れる」現象が起きます。後半のセクションが前半より雑にまとめられたり、フィールドが欠落したりします。
2. **ひとつの悪いフィールドが、レコード全体を汚染します。** 「acceptance criteria」がハルシネーションを起こすと、そのフィールドだけが失われるのではなく、レコード全体がレビュー対象として隔離されます。
3. **レイテンシが上がり、並列度が下がります。** 30k トークンの単一コールはかかる時間がかかります。シャーディングできません。

長いプロンプト、より多い例、厳格なフォーマットルール — 私もこれらで戦いました。これで信頼性は 10% くらい上がりますが、プロンプトエンジニアリングに大量の時間がかかります。

そして構造的な問題は消えません。

## 今やっていること: 分割する

私が使っているパターンは、伸びるアコーディオンのような形です。

```
[ document ]
     │
     ▼
[ Stage 1: segment ]   ← ひとつのプロンプト、ひとつの仕事: リストを生成する
     │
     ▼
[ array of segments ]
     │
     ▼ (fan out)
[ Stage 2: extract ]   ← ひとつのプロンプト、セグメントごとに実行
     │
     ▼
[ structured records ]
```

Stage 1 はドキュメント全体を読んで、セグメントの綺麗な配列を返します。セクション、段落、行アイテム — その仕事に合った単位なら何でも構いません。

Stage 2 はセグメントをひとつずつ受け取り、本当に欲しい構造化フィールドを抽出します。

プロンプトはふたつ、それぞれがひとつの仕事をします。

---

## なぜこちらの方がうまくいくのか

**各プロンプトに仕事がひとつだけ。**
Stage 1 は「境界を見つける」、Stage 2 は「スキーマを抽出する」。どちらのプロンプトもふたつのアイデアを同時に持つ必要がありません。それぞれをタイトに書けます。例文も短く、的確になります。

**エラーが局所化されます。**
Stage 2 がセグメント 7 で失敗したら、セグメント 7 だけを再実行します。ドキュメント全体をやり直す必要はありません。悪いフィールドはひとつのレコードに閉じ込められ、バッチ全体を汚染しません。

**Stage 2 は自然に並列化されます。**
Stage 1 の出力は配列です。Fan out させて、大きなコールひとつではなく、小さな抽出を 50 個並列で走らせます。総処理時間が下がり、ばらつきも減ります。

**キャッシュヒットが増えます。**
同じセグメントが 2 回出てきたら(テンプレート、標準ヘッダー、繰り返しのフォームなど)、Stage 2 は同じ入力を見るのでキャッシュが効きます。太ったプロンプト版では、毎回ドキュメント全体がユニークな入力として扱われます。

**長いドキュメントが怖くなくなります。**
太ったプロンプトの硬い制約はモデルのコンテキストウィンドウです。アコーディオンパターンにはこの天井がありません。Stage 1 はドキュメント全体を読みますが、その出力は小さい。Stage 2 はひとつのセグメントしか見ません。

---

## コストもあります

タダではありません。

LLM コール数が増えます — Stage 1 が 1 回に Stage 2 が N 回、合計 N+1 回のコール。短い入力では無駄になります。アコーディオンパターンは、太ったプロンプトが壊れ始めるくらい長いドキュメント向けで、2 段落のメール向けではありません。

「セグメントとは何か」を、自分のタスクに対して少し考える必要もあります。セクション見出しのこともあります。テーブルの行のこともあります。可視の境界に対応しない論理的な単位のこともあります。これは設計判断で、結構効きます。

---

## 使うとき

アコーディオンに手を伸ばすのは、こんなとき。

* ドキュメントが長くて、モデルが途中で筋を見失うのを観測している
* 出力スキーマのフィールドが 5 つ以上あって、それぞれが同じコンテキストを必要としていない
* 失敗したレコードだけ再実行したい(成功したものはそのまま残したい)
* 並列化したい

太ったプロンプトのままで良いのは、こんなとき。

* 入力が短く、スキーマも小さい
* フィールド同士が密に結合している(ひとつの抽出が他のフィールドのコンテキストを必要とする)
* プロトタイピング中で、まだ気にしていない

## 小さな具体例

私は StructFlow というサービスでこれを動かしています。コールの形はだいたいこんな感じ。

```
# Stage 1: segment
curl -X POST https://gw.ldxhub.io/structflow/jobs \
  -H "Authorization: Bearer $KEY" \
  -d '{
    "model": "google/gemini-3-flash-preview",
    "system_prompt": "Split this document into logical sections. Return one JSON record per section.",
    "example_output": { "section_title": "...", "section_text": "..." },
    "inputs": [{ "id": "doc1", "data": { "text": "..." } }]
  }'
```

レスポンスとして配列が返ってきます。次に Stage 2:

```
# Stage 2: extract (one call per segment, run in parallel)
curl -X POST https://gw.ldxhub.io/structflow/jobs \
  -H "Authorization: Bearer $KEY" \
  -d '{
    "model": "google/gemini-3-flash-preview",
    "system_prompt": "From this section, extract: purpose, mentioned services, acceptance criteria.",
    "example_output": { "purpose": "...", "mentioned_services": [], "acceptance_criteria": [] },
    "inputs": [{ "id": "sec1", "data": { "section_text": "..." } }]
  }'
```

ふたつのコール、それぞれが集中している。片方はセグメントを返し、もう片方は各セグメントを構造化フィールドに変えます。

これでパターン全体です。

## なぜこれを書いたのか

[LDX hub](https://gw.portal.ldxhub.io/introduction) を作ったのは、このパターンを動かしやすくする目的の一部でした — ひとつの API、非同期ジョブ、ファイルベースの I/O によって Stage 1 の出力が直接 Stage 2 の入力として使える、という形。ただし、パターン自体はどの特定のツールにも依存しません。生の OpenAI コール、Anthropic コール、プロンプトを受け取ってテキストを返すものなら何でも、これで動きます。

伝えたいのは「私の API を使ってください」ではありません。**長い入力で構造化抽出が不安定になっているなら、答えはおそらく長いプロンプトではなく、ふたつのプロンプトです。**
