![](https://static.zenn.studio/user-upload/0c34469a0dcd-20260502.png)
ほとんどの構造化データ抽出のチュートリアルは似たり寄ったりです。ドキュメントを用意し、「A、B、C、D、E、Fを抽出せよ」という一つの大きなプロンプトを書き、JSONを受け取る。それで終わりです。

これは短い入力に対しては機能します。

しかし、長い入力になると密かに破綻します。

本番環境でしばらく運用した後、私はこのやり方をやめました。私が何に切り替えたのか、そしてその理由をここに記します。

---

## 巨大プロンプトの問題

例えば、50ページのレポートがあり、そこから構造化された要約を得たいとします。自然な最初の一手は、次のようなものでしょう。

```
抽出内容:
- タイトル
- セクション（見出し付き）
- 目的
- 言及されているサービス
- 受入基準
- ...
この形式でJSONを返してください: { ... }
```

ドキュメント全体をモデルに渡します。JSONが返されます。最初の試行では問題ないように見えます。

その後、規模を拡大すると、3つのことが起こります。

1. **品質の低下。** モデルがドキュメントの途中で「忘却」してしまいます。後半のセクションの要約が前半より悪化したり、フィールドが欠落したりします。
2. **1つの不良フィールドがコール全体を台無しにする。** 「受け入れ基準」でハルシネーションが発生すると、そのフィールドを失うだけでなく、レコード全体がレビューのために隔離されることになります。
3. **レイテンシが上がり、並列性が下がる。** 1回で3万トークンのコールを行うと、それ相応の時間がかかります。これを分割（シャード）することはできません。

プロンプトを長くしたり、例を増やしたり、フォーマット規則を厳格にしたりすることでこれに対抗できます。私もそうしました。それにより信頼性は10%ほど向上するかもしれませんが、プロンプトエンジニアリングに多大な時間を費やすことになります。

構造的な問題は解消されません。

---

## 現在私が行っていること：分割する

私が使用しているパターンは、広がるアコーディオンのような形をしています。

```
[ ドキュメント ]
     │
     ▼
[ ステージ 1: 分割 ]   ← 1つのプロンプト、1つのタスク: リストを生成する
     │
     ▼
[ セグメントの配列 ]
     │
     ▼ (ファンアウト)
[ ステージ 2: 抽出 ]   ← 1つのプロンプト、セグメントごとに実行
     │
     ▼
[ 構造化されたレコード ]
```

ステージ 1 ではドキュメント全体を読み込み、セグメント（セクション、段落、ラインアイテムなど、タスクに適した単位）のクリーンな配列を返します。

ステージ 2 では一度に 1 つのセグメントを取り込み、実際に必要な構造化フィールドを抽出します。

2 つのプロンプトが、それぞれ 1 つのことを実行します。

---

## なぜこれがより効果的なのか

**各プロンプトには単一の役割があります。**
ステージ1は「境界を見つける」ことです。ステージ2は「スキーマを抽出する」ことです。どちらのプロンプトも、両方のアイデアを同時に保持する必要はありません。それぞれを厳密に記述できます。例はより短く、より的確になります。

**エラーが局所化されます。**
セグメント7でステージ2が失敗した場合、セグメント7のみを再実行します。ドキュメント全体をやり直す必要はありません。不良なフィールドは1つのレコードに隔離され、バッチ全体を汚染することはありません。

**ステージ2は自然に並列化されます。**
ステージ1の出力は配列です。これを展開してください。1つの大きな抽出ではなく、50の小さな抽出を並列に実行します。総実時間は短縮され、ばらつきも減少します。

**キャッシュヒット率が上がります。**
同じセグメントが2回現れた場合（テンプレート、標準ヘッダー、繰り返されるフォームなど）、ステージ2は同じ入力を認識するため、キャッシュを利用できます。巨大なプロンプトを使用するバージョンでは、ドキュメント全体が毎回1つのユニークな入力として認識されます。

**長いドキュメントが怖くなくなります。**
巨大なプロンプトのハードリミットは、モデルのコンテキストウィンドウです。アコーディオンパターンにはその上限がありません。ステージ1は依然としてドキュメント全体を読み取る必要がありますが、その出力は小さくなります。ステージ2は常に1つのセグメントのみを認識します。

---

## コストについて

無料ではありません。

LLMの呼び出し回数が増えます。1回で済むところを、ステージ1で1回、さらにステージ2でN回呼び出すことになります。短い入力に対しては無駄が多くなります。アコーディオンパターンは、太ったプロンプトが失敗し始めるほど長いドキュメントのためのものであり、2段落のメールのためのものではありません。

また、自分のタスクにとって「セグメント」とは何かをもう少し深く考える必要があります。セクションの見出しであることもあれば、表の行であることもあります。目に見える境界には対応しない論理的な単位であることもあります。これは設計上の決定事項であり、重要な意味を持ちます。

---

## いつ使うべきか

以下のような場合にアコーディオンパターンを検討してください：

* ドキュメントが十分に長く、モデルが途中で文脈を見失うのを確認した場合。
- 出力スキーマに5つ以上のフィールドがあり、それらすべてが同じコンテキストを必要としない場合。
- 成功したレコードをやり直すことなく、失敗したレコードのみを再試行する必要がある場合。
- 並列処理を行いたい場合。

次のような場合は、1つの巨大なプロンプトを使い続けてください：

* 入力が短く、スキーマが小さい場合。
- フィールドが密結合している場合（一方を抽出するのにもう一方の文脈が必要な場合）。
- プロトタイピングの段階で、まだ詳細を気にしていない場合。

## 小さな具体例

私はこれをStructFlowというサービスで実行しています。コールの形式はおおよそ以下の通りです：

```
# ステージ 1: セグメント
curl -X POST https://gw.ldxhub.io/structflow/jobs \
  -H "Authorization: Bearer $KEY" \
  -d '{
    "model": "google/gemini-3-flash-preview",
    "system_prompt": "このドキュメントを論理的なセクションに分割してください。セクションごとに1つのJSONレコードを返してください。",
    "example_output": { "section_title": "...", "section_text": "..." },
    "inputs": [{ "id": "doc1", "data": { "text": "..." } }]
  }'
```

レスポンスとして配列が返されます。次にステージ2です：

```
# ステージ 2: 抽出 (セグメントごとに1回呼び出し、並列実行)
curl -X POST https://gw.ldxhub.io/structflow/jobs \
  -H "Authorization: Bearer $KEY" \
  -d '{
    "model": "google/gemini-3-flash-preview",
    "system_prompt": "このセクションから、目的、言及されているサービス、受け入れ基準を抽出してください。",
    "example_output": { "purpose": "...", "mentioned_services": [], "acceptance_criteria": [] },
    "inputs": [{ "id": "sec1", "data": { "section_text": "..." } }]
  }'
```

2つの呼び出しを行い、それぞれに役割を集中させます。1つはセグメントを返し、もう1つは各セグメントを構造化されたフィールドに変換します。

パターンはこれだけです。

---

## なぜこれを投稿しているのか

私が [LDX hub](https://gw.portal.ldxhub.io) を構築した理由の一つは、このパターンを簡単に実行できるようにするためです。1つのAPI、非同期ジョブ、ファイルベースの入出力により、ステージ1の出力をステージ2の入力として直接利用できます。しかし、このパターン自体は特定のツールに依存しません。生のOpenAI呼び出し、Anthropic呼び出し、プロンプトを受け取ってテキストを返すものであれば何でも可能です。

ここでの教訓は「私のAPIを使ってください」ということではありません。**「長い入力に対して構造化抽出が不安定になっている場合、その解決策はおそらくプロンプトを長くすることではなく、プロンプトを2つに分けることである」**ということです。
